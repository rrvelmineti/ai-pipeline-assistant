# Deploy to Render (free tier)

[![Deploy to Render](https://render.com/images/deploy-to-render-button.svg)](https://render.com/deploy?repo=https://github.com/rrvelmineti/ai-pipeline-assistant)

The repository includes a Render Blueprint, [`render.yaml`](../../render.yaml). It creates:

- **claims-onboarding-platform**: a free web service built from the [`Dockerfile`](../../Dockerfile);
- **claims-onboarding-db**: a free PostgreSQL 16 database that only Render's own services can reach.

On the first start the database is empty, so the app loads the synthetic demo (scenarios A–F) in
the background: seven clients at every stage of onboarding. Synthetic data only. This pilot is not
HIPAA-compliant.

## Steps

1. Sign in at [render.com](https://render.com) with your GitHub account.
2. Click the **Deploy to Render** button above, or in the dashboard choose **New > Blueprint** and
   pick the `ai-pipeline-assistant` repository. Render reads `render.yaml` and shows the web service
   and the database.
3. Review the two resources (both on the free plan) and confirm. The first build takes several
   minutes (it builds the interface and installs Python packages).
4. When the service shows **Live**, open its URL (`https://claims-onboarding-platform-….onrender.com`).
   The demo finishes loading within a few minutes of the first start; `/api/health` shows
   `"demo": "running"`, then `"ready"`.
5. Find the password: open the web service, **Environment**, and reveal `CLAIMS_DEMO_PASSWORD`.
   Every demo user signs in with it: `admin`, `ana` and `sam` (analysts), `priya` and `omar`
   (approvers), `birch.contact` and `fir.contact` (client contacts).

Pushes to `main` redeploy automatically.

If `/api/health` shows `"demo": "failed"`, the service's **Logs** tab has the reason. After a fix is
deployed, the app clears the half-loaded demo and loads it again on its next start, but only if the
database holds nothing except demo users and demo clients; real work is never cleared.

## What the free tier means for this app

| Free-tier behaviour | Effect here |
| --- | --- |
| The service sleeps after 15 minutes without traffic | The first visit after a quiet spell waits about a minute while it wakes up |
| The local disk is wiped on every restart, deploy or sleep | Uploaded files are kept, encrypted, in PostgreSQL instead (`CLAIMS_FILE_STORE=database`), so nothing is lost |
| No shell access | The administrator and demo are created automatically on the first start instead of with the CLI |
| 750 free instance hours per workspace per month | Enough for one service running all month |
| Free PostgreSQL: 1 GB, no backups, **expires 30 days after creation** | After 30 days the database becomes inaccessible; Render deletes it 14 days later unless it is upgraded |

To keep the demo going after the database expires, delete the expired database and sync the
Blueprint again from its page in the dashboard, which creates a new free database with the same
name; then redeploy the web service. The app finds an empty database and loads the demo again.
Data from the old database is not carried over.

Source: Render's [free tier documentation](https://render.com/docs/free), checked 17 November 2026.
Render's limits can change; check that page before relying on them.

## Settings the Blueprint uses

| Variable | Value | Why |
| --- | --- | --- |
| `CLAIMS_DATABASE_URL` | From the database | Render's `postgresql://` URL; the app adds the driver name itself |
| `CLAIMS_ENCRYPTION_KEY` | Generated by Render | Any secret of 32+ characters is turned into the encryption key. **Never change it**: stored files and values would become unreadable (see [key rotation](runbooks.md#rotate-the-encryption-key)) |
| `CLAIMS_DEMO_PASSWORD` | Generated by Render | Password for every demo user |
| `CLAIMS_SEED_DEMO` | `1` | Load the demo when the database is empty |
| `CLAIMS_FILE_STORE` | `database` | Keep uploads in PostgreSQL |

The image itself sets `CLAIMS_ENV=production` (an encryption key is required) and
`CLAIMS_SIMULATION=0` (the fault-injection endpoint used by the test scenarios is switched off).

## Before sharing the link

- The demo password opens every account, **including the administrator**. To show the platform
  to someone, sign in as `admin` and create them their own account with a role that fits, rather
  than sharing the password.
- Anyone with an account can upload files. Keep it to synthetic data; there is no way for the
  platform to tell real data from synthetic.
- To start with only an administrator and no demo data, set `CLAIMS_SEED_DEMO` to `0` and add
  `CLAIMS_ADMIN_PASSWORD` before the first start (on an empty database).
