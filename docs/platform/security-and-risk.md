# Security and risk assessment

**Scope:** pilot v1.0 as built in this repository. **Assessed by:** the delivery team, as a design
review backed by automated tests, not an independent penetration test.

## Compliance position

- **This platform is not HIPAA-compliant** and has not been assessed against HIPAA, HITRUST, SOC 2
  or any other framework. It must not receive real protected health information.
- All data in the repository and the demo is **synthetic**: generated by code, with no real people,
  providers or claims.
- Several controls below are ones a compliant system would need, but having them does not make the
  system compliant. A compliance assessment, a business associate agreement with every processor,
  and an independent security test are prerequisites for any real data.

## Data handled

| Data | Where | Protection |
| --- | --- | --- |
| Uploaded claims files | File store | Fernet-encrypted; stored under client ID and content hash; never served back by the API |
| Finding values (the cell that broke a rule) | Database | Fernet-encrypted; decrypted only for users with access to the client |
| Client letters | Database | Fernet-encrypted bodies |
| Records loaded downstream | Database (simulated system) | Fernet-encrypted payloads |
| Mappings, rule text, counts, audit entries | Database | Not encrypted: they contain column headings and counts, not cell values |
| Passwords | Database | scrypt hashes only |
| Session tokens | Database | SHA-256 digests only |

What is sent to Gemini, only when a user asks: column headings, field descriptions, rule text, row
counts and the fixed fix-it text. Never cell values, claim IDs, member IDs, dates or amounts. A test
inspects the request bodies to confirm this.

## Threats and controls

| # | Threat | Control | Tested by |
| --- | --- | --- | --- |
| T1 | A user reads another client's data | Per-user client access list; other clients' records return 404 | F1, F2, F3 |
| T2 | A client contact changes decisions | Role checks on every route; contacts can upload and add notes only | F4 |
| T3 | Password guessing | Lockout after 5 failures; scrypt; same response for unknown user and wrong password | F6, `test_unknown_and_wrong_password_look_the_same` |
| T4 | Stolen session token | 8-hour expiry; revoked on sign-out, password change or disable; only digests stored | F8, `test_expired_session_is_refused` |
| T5 | One person pushes through their own change | Four-eyes on mappings, rules and go-live, including administrators | C4, F7, `test_go_live_needs_an_independent_approver` |
| T6 | Approval despite known problems | Readiness checks block approval; blockers cannot be waived; warnings need a reason | B4, B5, `test_warning_must_be_dispositioned_before_go_live` |
| T7 | Someone edits or deletes audit history | Hash chain with a locked head; verification detects edits and deletions at the end | F10, `test_audit_tampering_is_detected`, `test_deleting_the_newest_audit_entries_is_detected` |
| T8 | Theft of the database or file store | Values and files encrypted with a key held outside the database | `test_uploaded_files_and_finding_values_are_encrypted_at_rest` |
| T9 | Malicious file names or CSV content | File names sanitised; values never executed; formula characters neutralised in CSV downloads | `test_upload_filename_is_sanitised`, `test_csv_export_neutralises_spreadsheet_formulas` |
| T10 | Script injection in the interface | React escapes output; CSP forbids inline and third-party scripts; no `dangerouslySetInnerHTML` | Headers test; code review |
| T11 | Duplicate or lost claims downstream | Idempotent batches, per-claim uniqueness, resumable exports | A4, E8, E9, E10 |
| T12 | AI gives a wrong mapping or invents figures | AI only suggests; uncertain fields need confirmation and approval; reworded text with new numbers is rejected | C1, C2, `test_ai_explanation_sends_no_cell_values_and_rejects_invented_figures` |
| T13 | Fault injection left on | Off by default in the Docker image; endpoint returns 404 when off; admin-only when on | Manual check in production mode |

## Known gaps (accepted for the pilot)

| Gap | Risk | Before real use |
| --- | --- | --- |
| No TLS in the application | Tokens and data readable on the network | Terminate TLS at a proxy or load balancer |
| Token in browser session storage | Readable by script if an XSS flaw existed | Move to an HttpOnly, SameSite cookie with CSRF protection |
| No multi-factor authentication or single sign-on | Password-only accounts | Integrate the organisation's identity provider |
| Encryption key in an environment variable | Key exposure via the host | Use a key management service; rotate on a schedule |
| Audit chain can be rebuilt by someone with database write access and the code | A determined administrator could forge history | Ship audit entries to write-once storage or an external log |
| Single process, no rate limiting beyond lockout | Easy to exhaust | Rate limiting at the proxy; job queue for background work |
| Upload size is checked after the request body is received | A very large upload uses disk and time before it is refused | Set a request body limit (for example 25 MB) at the proxy |
| No data retention or deletion schedule | Files kept indefinitely | Agree retention; add purge jobs |
| Dependencies not scanned in CI | Known vulnerabilities could slip in | Add `pip-audit` and `npm audit` to CI |
| Not independently tested | Unknown flaws | Penetration test before any real data |

## Risk register (delivery)

| Risk | Likelihood | Impact | Mitigation | Owner |
| --- | --- | --- | --- | --- |
| Someone uploads real data to the pilot | Medium | High | Banners on every screen and the sign-in page; synthetic-only rule in onboarding; restrict access to the team | Implementation lead |
| Mapping approved without real checking | Medium | Medium | Confirmation ticks, correction log, four-eyes, comments in the audit trail | Approver |
| Rules do not reflect what the claims system needs | Medium | High | Rule owner reviews baseline; versioned changes with reasons | Product owner |
| KPIs quoted as savings without a baseline | Medium | Medium | Baseline method documented; dashboard states no saving is claimed | Sponsor |
| Single-process limits reached in a larger pilot | Low | Medium | 100,000-row run measured; job queue on the roadmap | Engineering |
